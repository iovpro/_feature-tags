# Регламент фич-хэштегов

Хэштег в коде связывает объявление с флоу из реестра (`features.md` в корне репозитория) — трассировка
цепочки по исходнику, а не в runtime. Теги задают состав цепочки; порядок шагов — только в реестре.
Даёт: поиск кода флоу, перечень точек входа, определение затронутых цепочек при изменениях
и формирование QA scope — проверки и правила scope в [checks.md](checks.md).

Регламент **не зависит от языка, репозитория и проекта**: ядро (этот файл) описывает формат и правила в терминах
«объявление», «тег-строка», «тег-группа», «ветка», «тест»; ничего специфичного для конкретного проекта в нём нет,
примеры — иллюстрации. Привязка к конкретному языку — в [langs/](langs/) (по файлу на язык); индекс и таблица
соответствия полей — в [langs.md](langs.md).

> **Применяется безусловно.** Этот регламент действует при любой доработке кода — включая быстрые
> фиксы и работу без задачи, во всех репозиториях проекта.

## Термины

| Термин     | Значение                                                                                                                                                        |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Флоу       | Цепочка работы кода от точки входа до результата                                                                                                    |
| Объявление | Именованная единица кода или конфигурации, за которой стоит поведение: функция, метод, тип, класс, модуль-хендлер, ресурс манифеста, сервис compose, SQL-объект |
| Тег-строка | Однострочный комментарий, содержащий **только** теги. Синтаксис комментария — по языку                                                                          |
| Тег-группа | Отдельная comment group из одной тег-строки. Стоит перед документацией, декораторами и объявлением и отделяется от них пустой строкой                           |
| Ветка      | Вариант внутри одного объявления: `case`, `if`/`elif`, match-arm. Тег ставится хвостовым комментарием на строке ветки                                           |
| Тест       | Единица тестирования по конвенции языка: тест-функция, `it`/`test`-кейс, `@test`. Как её распознать — по языку                                                  |

## Формат

```
#f:<домен>.<фича>.<флоу>[.<шаг>[.<подшаг>…]][@<маркер>]
```

| Уровень | Что это                                                                                       | В реестре   |
| ------- | --------------------------------------------------------------------------------------------- | ----------- |
| домен   | **Владелец** флоу — домен, в чьей спецификации флоу описан. Не место кода                     | обязательно |
| фича    | Функциональная область внутри домена                                                          | обязательно |
| флоу    | Цепочка с началом и результатом, либо самостоятельная операция, используемая несколькими флоу | обязательно |
| шаг     | Фаза или ветка цепочки: `send`, `recv`, `ack`, `persist`, `verify`. Глубина не ограничена     | не вносится |

- Сегменты — только `[a-z0-9]`, разделитель `.`. Рекомендуемый максимум — 5 сегментов.
- **Домен = владелец, не расположение.** Код `billing.invoice.create` в пакете API — норма:
  биллинг инициирует создание счёта, значит домен — `billing`. При сомнении — домен инициатора.
  Владелец не зависит и от репозитория: один флоу может проходить через несколько репозиториев.
- **Домены не могут быть префиксами друг друга** — иначе префиксный поиск даст мусор.
- Флоу заводится **только через реестр**: сначала запись в `features.md`, потом тег в коде.
  Шаги (4-й сегмент и глубже) в реестр не вносятся — это локальное уточнение внутри флоу.

### Маркеры

Маркер — суффикс тега. Суффикс, а не отдельный префикс, чтобы префиксный поиск находил точки входа
вместе с остальным кодом флоу.

| Маркер       | Значение                                                                                                                                                                  | Обязателен                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `@entry`     | Внешний стимул запускает флоу: API-хендлер, CLI-команда, таймер, входящее сообщение, начинающее новую цепочку, UI-действие, запускаемый job/service/resource              | один из двух стартовых маркеров |
| `@operation` | Точка входа в самостоятельную переиспользуемую операцию: публичная функция примитива, старт внутреннего lifecycle или подфлоу                                             | один из двух стартовых маркеров |
| `@recv`      | Уже начатый флоу продолжается после перехода между процессами или репозиториями: приёмный хендлер на другом узле, backend после запроса frontend, локальный API после CLI | нет                             |

Правила маркеров:

1. Реализованный флоу (`partial`/`done`) — хотя бы одна стартовая точка `@entry` или `@operation`.
2. Оба маркера на одном флоу допустимы, если он доступен извне и переиспользуется как операция.
3. Приёмный хендлер на другой стороне — `@recv`, не новая точка входа: иначе список стартов замусорится.
4. Терминальные состояния не помечаются — результат определяется логикой объявления и тестами,
   а не комментариями внутри функции.
5. Маркеры — только на production-объявлениях уровня флоу (включая **запускаемые** конфигурационные
   ресурсы; описательные ресурсы маркеров не получают).
   Тесты подтверждают флоу, но не являются production-точкой входа; типы с тегом фичи маркеров не получают.
6. `@operation` — на корневом вызываемом объявлении, не на внутренних функциях реализации.

Имена `@entry` и `@operation` не являются префиксами друг друга — точный поиск одного маркера
не смешивает внешние и внутренние старты.

## Реестр

Реестр флоу — файл `features.md` в корне кодового репозитория. Каждый репозиторий ведёт свой реестр.
Флоу, проходящий через несколько репозиториев, регистрируется в реестре каждого из них — везде, где есть
его теги. Стартовый маркер стоит в одном репозитории; в остальных цепочка продолжается с `@recv`, а проверка
стартовой точки для таких флоу отключается в `.ftags.conf` (`NOSTART_IGNORE`).
Структура: раздел на домен, таблица «Тег · Описание · Спека · Статус», для флоу в описании — цепочка.

Статусы флоу:

| Статус       | Значение                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `planned`    | Флоу описан, реализация не начата                                                                                         |
| `partial`    | Флоу реализован частично                                                                                                  |
| `done`       | Флоу реализован полностью                                                                                                 |
| `deprecated` | Флоу запрещён для нового использования; может временно оставаться для совместимости или храниться в реестре как tombstone |

Для `deprecated` в описании обязательно указывается замена либо условие окончательного удаления. Теги
оставшегося compatibility-кода разрешены, но добавление новых тегов или dependency edges на
deprecated-флоу считается нарушением.
Стартовый маркер для tombstone без кода не требуется.

### Зависимости флоу

Таблица реестра «Флоу-потребитель · Использует» фиксирует **прямые семантические зависимости** между
флоу, а не каждый вызов функции. Направление записи: потребитель → используемая операция.
Распространение изменения — обратное транзитивное замыкание по таблице:

```text
изменилась операция → её прямые потребители → их потребители → … = affected в QA scope
```

Пример: изменилась `crypto.sign.verify` — затронуты она сама (`changed`), использующие её флоу и их
потребители (`affected`). Нарушения целостности таблицы: неизвестная ссылка, self-reference, дубликат связи.

## Иерархия = префикс строки

Никакой отдельной структуры для иерархии не нужно — она заложена в самой строке тега.
Граничный класс `([.@ ]|$)` учитывает маркеры. Поиск одинаков для любого языка: тег — это подстрока.

```bash
grep -rnE '#f:billing([.@ ]|$)'                    .   # весь домен
grep -rnE '#f:billing\.invoice([.@ ]|$)'           .   # фича со всеми флоу
grep -rnE '#f:billing\.invoice\.create([.@ ]|$)'   .   # флоу со всеми шагами
grep -rn  '#f:auth.login.oauth@entry'              .   # внешние точки входа
grep -rn  '#f:crypto.sign.verify@operation'        .   # вход во внутреннюю операцию
grep -rnE '#f:order\.checkout\.submit(\.[a-z0-9]+)*@recv([[:space:]]|$)' . # продолжения на другой стороне
```

Маски файлов и исключения (vendor, сгенерированное) — по языку, см. [langs/](langs/).

## Куда и как ставить

Тег не является документацией объявления и в генерируемую документацию не попадает: он стоит отдельной
comment group **перед** doc-comment, декораторами и атрибутами. Связь с ближайшим следующим объявлением
детерминирована — это цепочка строк без разрывов:

```text
тег-группа → ровно одна пустая строка → [doc-comment | decorators | attributes]* → объявление
```

```text
<comment-marker> #f:domain.feature.flow@entry

<doc-comment / decorators / attributes>
<declaration>
```

- Пустая строка после тег-группы обязательна и тогда, когда документации и атрибутов нет.
- Допустимые промежуточные строки задаёт профиль языка; любая другая строка, включая вторую пустую,
  разрывает связь.
- Единственное исключение — тег ветки диспетчера: хвостовой комментарий на строке ветки.

| Объект                                                                      | Тег                                                                                           |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Функция, метод, хендлер                                                     | Тег уровня **флоу** (≥ 3 сегмента), при необходимости с шагом и маркером                      |
| Тип, класс, интерфейс, константы, типы сообщений, схемы                     | Тег уровня **фичи** (2 сегмента). Помечается целиком                                          |
| Ресурс конфигурации (манифест, сервис compose, стадия Dockerfile, миграция) | Тег уровня **флоу** или **фичи** — в зависимости от того, несёт ресурс поведение или описание |
| Ветка диспетчера                                                            | Инлайн-тег уровня флоу на строке ветки — когда общий обработчик обслуживает несколько флоу    |
| Тест                                                                        | Теги флоу, которые тест проверяет. **Обязательно** — иначе точечный прогон не найдёт регресс-тесты |

**Запрещено:**

- Тег в шапке файла или модуля. Файловый тег ничего не говорит о том, какие объявления в каком флоу участвуют.
- Тег на поле структуры, свойстве класса, ключе манифеста. Состояние флоу помечается через тип или ресурс целиком.
- Голый доменный тег (`#f:ctl`) на любом объявлении.
- Тег внутри или в составе doc-comment/docstring языка (godoc, rustdoc, JSDoc и т. п.).
  Тег-группа всегда отделена от документации пустой строкой — см. [langs/](langs/).
- Текст на строке тега: описания, идентификаторы замечаний (`G16`, `R1-F08`), пояснения. Описание флоу
  живёт в реестре. Пояснение к объявлению — его обычный doc-comment после тег-группы.

Перечисленные запреты и сироты — классы находок `ftags check`; таблица классов, grep-рецепты и порядок
проверки — [checks.md](checks.md#классы-находок).

### Несколько флоу на одном объявлении

Одно объявление может участвовать в нескольких флоу — это нормально и именно это тегами и фиксируется.
Все теги объявления стоят **в одной тег-строке** через пробел, каждый со своим `#f:`, чтобы `grep -o`
вытаскивал их по отдельности.

**Примитивы не помечаются флоу потребителей.** Криптография, сериализация, IO-хелперы получают
собственный флоу (`crypto.sign.verify`) и не несут теги всех, кто их вызывает — иначе теги дрейфуют при
каждом новом потребителе. Связь потребителя с операцией фиксируется один раз в таблице зависимостей
реестра; конкретный вызов в коде служит подтверждением этой связи.

**Хелперы без собственной логики** (`writeJSON`, `printUsage`, форматирование вывода) тег не несут.

### Грамматика

```
тег        := "#f:" сегмент ("." сегмент)* ("@" маркер)?
сегмент    := [a-z0-9]+
маркер     := "entry" | "operation" | "recv"
тег-строка := <маркер комментария языка> " " тег (" " тег)* <конец строки>
```

Regex тега: `#f:[a-z0-9]+(\.[a-z0-9]+)*(@(entry|operation|recv))?`.
Тег-строка целиком — только теги после маркера комментария; для ветки — хвостовой комментарий той же формы.

Примеры размещения по языкам — в [langs/](langs/).

## Изменение флоу

| Операция                   | Порядок действий                                                                                                              |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Новый флоу                 | Запись в `features.md` с цепочкой и зависимостями → production-тег с подходящим стартовым маркером → тег без маркера в тестах |
| Новый шаг                  | Только тег в коде; реестр не трогается                                                                                        |
| Переименование             | Обновить реестр → заменить **все** вхождения во всех репозиториях одним проходом → проверка целостности                       |
| Deprecation                | Перевести запись в `deprecated`, указать замену/условие удаления; новые использования запрещены                               |
| Удаление                   | Сначала deprecation; затем убрать код и теги, оставив `deprecated`-запись как tombstone                                       |
| Декомпозиция               | Фича остаётся, добавляются флоу; теги на конкретном коде переезжают на флоу                                                   |
| Слияние                    | Обратная операция: теги переезжают на оставшийся флоу, лишний удаляется из реестра                                            |
| Новый язык или репозиторий | Файл в `langs/` и профиль `tool/langs/<язык>.conf` по чеклисту → `.ftags.conf` репозитория → теги                             |
