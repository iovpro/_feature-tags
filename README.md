# Фич-хэштеги

Регламент разметки исходного кода тегами функциональных цепочек — **флоу** — и ведения их реестра.
Тег в комментарии связывает объявление (функцию, тип, ресурс конфигурации, тест) с записью реестра
`features.md`. Цепочка прослеживается по исходнику: без запуска, без графа вызовов, без внешнего индекса.

Регламент не зависит от языка, репозитория и инструментов. Ядро сформулировано в терминах
«объявление», «тег-строка», «тег-группа», «ветка», «тест»; как эти термины ложатся на конкретный
язык — отдельными файлами в [langs/](langs/).

## Зачем

| Задача                                             | Как решается разметкой                                                                     |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Найти весь код цепочки                             | Иерархия заложена в строку тега — префиксный `grep` по домену, фиче или флоу               |
| Понять, откуда всё начинается                      | Точки входа помечены маркерами `@entry` и `@operation` и перечисляются одним поиском       |
| Понять, что сломает правка                         | Теги изменённых объявлений + таблица зависимостей реестра дают перечень затронутых флоу    |
| Собрать QA scope                                   | Затронутые флоу раскладываются по категориям `new` / `changed` / `affected` / `deprecated` |
| Держать каталог функциональности в актуальном виде | Реестр `features.md`: цепочка, ссылка на спеку и статус для каждого флоу                   |

## Как это выглядит

Реестр `features.md` — источник истины о составе функциональности:

```markdown
| Тег                         | Описание                                                                 | Спека             | Статус |
| --------------------------- | ------------------------------------------------------------------------ | ----------------- | ------ |
| `#f:billing.invoice.create` | REST-запрос → валидация заказа → расчёт позиций → запись счёта → событие | `docs/billing.md` | done   |
```

Код несёт теги флоу, в которых участвует объявление:

```go
// #f:billing.invoice.create@operation

// Create generates a new invoice for the given order.
func (s *InvoiceService) Create(orderID string, items []LineItem) (*Invoice, error) { ... }
```

Навигация — обычный поиск по подстроке, одинаковый для любого языка:

```bash
grep -rnE '#f:billing\.invoice([.@ ]|$)'         .   # фича целиком, со всеми флоу и шагами
grep -rn  '#f:billing.invoice.create@operation'  .   # точка входа
```

## Правила в двух словах

- Формат тега: `#f:<домен>.<фича>.<флоу>[.<шаг>…][@<маркер>]`, сегменты из `[a-z0-9]`.
- Домен — **владелец** флоу (чья спецификация его описывает), а не место, где лежит код.
- Флоу заводится только через реестр: сначала запись с цепочкой и зависимостями, потом тег в коде.
- Тег стоит отдельной comment group перед doc-comment и объявлением, отделённой пустой строкой,
  и не содержит ничего, кроме тегов. Тесты помечаются тегами флоу, которые они проверяют.
- У реализованного флоу есть стартовая точка: `@entry` — внешний стимул, `@operation` — переиспользуемая
  операция; `@recv` — продолжение цепочки на другой стороне процесса или репозитория.

Полные правила, маркеры, устройство реестра, запреты и порядок изменения флоу — [spec.md](spec.md).

## Внедрение

Репозиторий подключается git submodule под именем `_feature-tags/` — на уровне проекта
(мета-репозитория) для multi-repo или в корень кодового репозитория для single-repo:

```bash
git submodule add git@github.com:iovpro/_feature-tags.git _feature-tags
```

Дальше по [bootstrap.md](bootstrap.md): `.ftags.conf` с активными языками, шаблон `features.md`,
цели Makefile и ссылки в CLAUDE.md, чтобы AI-ассистенты применяли регламент при работе с кодом.

## Проверки

Разметка проверяема: сироты (теги вне реестра), посторонний текст в тег-строке, теги в шапке файла
и на полях, реализованные флоу без стартовой точки, нарушения таблицы зависимостей. Рецепты на голом
`grep` и правила формирования QA scope — [checks.md](checks.md).

Те же проверки автоматизирует инструмент [`ftags`](tool/README.md) — shell без сборки
(bash 3.2+, POSIX awk, grep, sed, git; macOS, Debian, Alpine; Windows — через WSL). Инструмент — часть
регламента: профили языков, `.ftags.conf` и цели Makefile обязательны; grep-рецепты — fallback без него.

```bash
tool/ftags.sh check                  # целостность разметки и реестра
tool/ftags.sh trace <флоу>           # объявления цепочки, сгруппированные по маркерам
tool/ftags.sh qa-scope --base <rev>  # что проверять после изменений
```
